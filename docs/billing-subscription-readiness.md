## 1. 문서 목적

이 문서는 꿈따라의 PG/구독 결제 기능을 구현하기 전, 요금제·권한·환불·개인정보·DB 상태 흐름을 미리 정리하기 위한 **기준 문서**다.

- 현재 결제 기능은 연결되어 있지 않다 (베타 운영 중).
- 이 문서는 결제 기능을 구현하지 않는다.
- 구현 작업자는 이 문서를 기준으로 별도 작업지시서를 받아야 한다.
- 법적 효력이 있는 문서가 아니며, 단정적 수치는 코드/기획 확정 후 갱신이 필요하다.

## 2. 현재 요금제 구조

### 2-1. 요금제 표 (코드 기준)

소스: `src/types/family.ts` (`PLAN_ENTITLEMENTS`), `src/app/pricing/page.tsx`

| 플랜명 | 코드 키 | 월 가격 | 자녀 수 (`child_limit`) | AI 상담 월 한도 | 명따라 연 한도 | 공동양육자 | 비고 |
|---|---|---|---|---|---|---|---|
| 베타 무료 체험 | `free` | 0원 | 1명 | 3회 | 없음 | 없음 | ✅ Migration 043으로 정규화 완료 (2026-05-21) |
| 베이직 | `basic` | 9,900원 | 1명 | 30회 | 3회 | 1명 | |
| 프리미엄 | `premium` | 14,900원 | 1명 | 100회 | 3회 | 1명 | 추천 플랜 |
| 패밀리 | `family` | 19,900원 | 2명 | 120회 (가구 기준) | 6회 | 1명 | |
| 패밀리 플러스 | `family_plus` | 24,900원 | 3명 | 200회 (가구 기준) | 9회 | 1명 | `child_limit=3` int not null |

### 2-2. AI 상담 한도 상세

- **AI 상담 사용량 집계 기준**: `parent_id + used_month` (가구 단위, 자녀별 분리 없음)
- **패밀리 "자녀당 60회" 표현 금지**: 코드상 parent 기준 집계이므로 자녀별 분리 불가
- **FREE_LIMIT 상수**: 코드 내 서버·클라이언트 양쪽에 `const FREE_LIMIT = 3` 하드코딩
- **유료 플랜 한도**: `subscription_plan.ai_consult_monthly_limit` DB 컬럼이 최종 기준

### 2-3. 명따라(사주 분석) 한도

- **연 제공 시점**: 1학기(3월) · 2학기(9월) · 연말(12월)
- **추적 방식**: `myeonddara_usage` 테이블 (연도별 집계, 구조 확인 필요)
- **무료 플랜**: 명따라 없음 (PLAN_ENTITLEMENTS 기준)

### 2-4. ✅ 해소됨: Free/Basic 명칭 혼선 (Migration 043, 2026-05-21)

**해소 전 현황**:
```typescript
// 구 코드 (036 버그수정 당시)
const FREE_PLAN_NAMES = new Set(["free", "basic"]);  // "basic"을 무료로 취급하는 임시 우회
const isFree = !plan || FREE_PLAN_NAMES.has(plan.plan_name);
```

**정규화 완료 후**:
```typescript
// 현재 코드 (043 정규화 이후)
const FREE_PLAN_NAMES = new Set(["free"]);  // free=무료, basic=유료베이직으로 명확 분리
const isFree = !plan || FREE_PLAN_NAMES.has(plan.plan_name);
```

**변경 내용**:
- `supabase/migrations/043_normalize_free_basic_plan_names.sql`: 기존 `plan_name='basic'` 전체 → `'free'` 보정
- `src/app/auth/callback/route.ts`: 신규 가입자 `plan_name="free"` 생성
- `src/app/api/ai-consult/route.ts`, `src/app/parent/counseling/page.tsx`: `FREE_PLAN_NAMES=["free"]` 단일화

- **신규 가입자 실제 DB 상태**: ~~`plan_name = "basic"`~~ → `plan_name = "free"`  
  (`auth/callback`이 신규 가입 시 `plan_name="basic"`으로 row를 생성)
- **코드상 처리**: `"basic"`을 무료로 취급, `FREE_LIMIT = 3` 적용
- **문제**: `"basic"`이 유료 베이직(9,900원)과 동일한 DB 키를 사용하므로, 결제 연동 시 유/무료 구분이 불명확해짐
- **결제 도입 전 반드시 해결**: 신규 가입자 plan_name을 `"free"`로 분리하거나, 유료 전환 시 명시적으로 구분하는 정책 확정 필요

## 4. 구독 상태 모델 초안

> **주의**: 현재 DB에 아래 상태를 추가하지 않습니다. 후속 migration 검토용 초안입니다.

### 4-1. 상태 정의

| 상태 | 의미 | 허용 기능 | 제한 기능 | 전환 조건 |
|---|---|---|---|---|
| `free` | 무료/베타 체험 | AI 상담 3회/월, 탐색 전체 | 유료 기능 제한 | 가입 시 기본값 |
| `trial` | 무료 체험 기간 | 유료와 동일 (기간 한정) | — | 별도 프로모션 적용 시 |
| `active` | 유료 구독 활성 | 플랜별 전체 기능 | — | 결제 성공 확인 후 |
| `past_due` | 정기결제 실패 | (정책 확정 필요: 즉시 차단 vs 유예) | — | webhook 결제 실패 수신 |
| `canceled` | 해지 완료 | 잔여 기간까지 서비스 유지 권장 | 갱신 없음 | 해지 요청 처리 후 |
| `expired` | 만료 | 무료 수준 또는 접근 차단 | 유료 기능 | `expires_at` 경과 후 |
| `refunded` | 환불 처리 완료 | 무료 수준 또는 차단 | 유료 기능 | 환불 확인 후 |

**현재 DB `status` 컬럼**: `"active" | "expired" | "cancelled"` — `past_due`, `trial`, `refunded` 상태 없음  
→ 결제 도입 전 `subscription_plan.status` 타입 확장 migration 검토 필요

### 4-2. 상태 전환 다이어그램

```
가입
  └─ free (기본)
        └─ 결제 성공 → active
              ├─ 정기결제 실패 → past_due → (재시도 성공) → active
              │                             → (유예 만료) → expired
              ├─ 해지 요청 → canceled (기간 내 서비스 유지) → expired
              ├─ 환불 처리 → refunded
              └─ expires_at 경과 → expired
                    └─ 재구독 → active
```

## 5. 결제 이벤트 흐름 초안

> **주의**: 실제 PG webhook 구현은 하지 않습니다. 흐름 정리 문서입니다.  
> **중요 보안 원칙**: 결제 성공 여부를 클라이언트 응답값만으로 신뢰해서는 안 됩니다. 반드시 webhook 서버 검증이 필요합니다.

### 5-1. 최초 결제 흐름

| 단계 | 사용자 화면 | 서버 처리 | DB 기록 | 실패 처리 |
|---|---|---|---|---|
| 1. 요금제 선택 | `/pricing` 카드 클릭 | — | — | — |
| 2. 결제창 진입 | PG SDK 결제창 로드 | 결제 요청 생성 | 주문 임시 생성 (확인 필요) | 결제창 로드 실패 안내 |
| 3. 결제 정보 입력 | PG 결제창 내 처리 | — | PG 측 처리 | PG 오류 안내 |
| 4. 결제 승인 | 승인 완료 페이지 | **webhook 수신 후** plan 업데이트 | `subscription_plan` 갱신 | CS 대응 필요 |
| 5. 권한 활성화 | 구독 확인 화면 | `subscription_plan.status = 'active'` | — | webhook 재시도 대기 |

### 5-2. 정기결제 갱신 흐름

| 단계 | 처리 | 주의 |
|---|---|---|
| 자동 갱신일 | PG에서 자동 청구 | 사용자 개입 없음 |
| 성공 webhook | `expires_at` 연장 | 중복 이벤트 방지 처리 필요 |
| 실패 webhook | `status = 'past_due'` | 유예 기간 정책 확정 필요 |
| 재시도 성공 | `status = 'active'` 복원 | — |
| 최종 실패 | `status = 'expired'` | 사용자 알림 + CS 안내 |

### 5-3. 해지 흐름

| 단계 | 처리 | 주의 |
|---|---|---|
| 해지 요청 | `status = 'canceled'` 예약 | 즉시 차단 vs 기간 내 유지 정책 확정 필요 |
| 기간 종료 | `status = 'expired'` | 자동 처리 또는 수동 확인 |
| 재구독 가능 | `status = 'active'`로 전환 | — |

### 5-4. 환불 흐름

| 단계 | 처리 | CS 포인트 |
|---|---|---|
| 환불 요청 수신 | CS 확인 → PG 환불 API 호출 | 24시간/7일 기준 확인 |
| PG 환불 처리 | PG에서 취소 완료 (3~5영업일) | 카드 취소 안내 필요 |
| 권한 처리 | `status = 'refunded'` 또는 즉시 `expired` | 정책 확정 필요 |
| 사용량 처리 | 당월 사용분 기록 유지 vs 초기화 | 정책 확정 필요 |

### 5-5. Webhook 처리 원칙

- **webhook 엔드포인트 서명 검증 필수** (PG별 방식 상이)
- **중복 이벤트 방지**: webhook 이벤트 ID 기록, 동일 ID 재처리 차단
- **재시도 대비**: webhook 처리 실패 시 PG에서 재전송 — 멱등성 보장 필요
- **클라이언트 결과값 신뢰 금지**: 결제 성공 여부는 반드시 webhook으로만 확정

## 6. 권한 적용 기준

### 6-1. 기능별 권한 현황
