### 3.1 심화 기준 직업(4개)의 공통 구조

`docs/occupation-content-axis-standard.md`가 이미 정의한 기준을 실제 코드(`src/app/explore/[id]/page.tsx`)와 대조한 결과:

| 항목 | 심화 4개 직업(webtoon-artist/creator/veterinarian/chef) | 일반 직업(나머지 123개) |

| 꿈 지도형 요약(4탭) | 있음 — `OCCUPATION_DEPTH_SEED[id]` 존재 시에만 `DreamMapHub` 렌더 | 없음 — `dreamMapDepth`가 `null`이면 허브 자체가 미노출(하드코딩 대체 없음, 안전한 폴백) |

### 3.2 코드상 게이트 3중 구조

심화 4탭이 화면에 뜨려면 아래 3가지가 **모두** 충족되어야 한다(`isDreamMapActive = isTargetOccupation && viewerModeState.mode === "compass"`, `isTargetOccupation = FEATURE_FLAGS.DREAM_MAP_ENABLED && DREAM_MAP_OCCUPATION_IDS.includes(id)`):

1. `NEXT_PUBLIC_DREAM_MAP_ENABLED === "true"`(feature flag, 기본 OFF)
2. `DREAM_MAP_OCCUPATION_IDS`에 slug 등록(현재 `webtoon-artist` 1개뿐)
3. 로그인 사용자의 활성 자녀 `grade_level`이 나침반(초5~고등) 모드일 것

**따라서 `creator`/`veterinarian`/`chef`는 `OCCUPATION_DEPTH_SEED`에 콘텐츠가 이미 존재함에도, 2번 화이트리스트에 없어 어떤 사용자·어떤 모드로도 화면에 노출되지 않는다.** 이는 콘텐츠 누락이 아니라 **작성된 콘텐츠가 게이트에 막혀 검증·노출되지 못하는 상태**이며, 전수 적용 설계 시 반드시 구분해야 한다(§9 위험 요소 참고).

| **완전 충족 + 노출 가능** | 1개(`webtoon-artist`) | 4탭 콘텐츠 + 화이트리스트 등록 + (flag ON 시) 실제 화면 노출까지 전 구간 검증됨(A13-PRE2에서 브라우저 실측 완료) |
| **완전 충족 + 노출 불가(게이트 막힘)** | 3개(`creator`, `veterinarian`, `chef`) | 4탭 콘텐츠는 있으나 `DREAM_MAP_OCCUPATION_IDS` 미등록으로 화면에 뜨지 않음 |
| **부분 충족(정적/퀴즈만)** | 122개(126 합집합 − 4개 심화 대상 직업) | `OCCUPATIONS`와 `QUIZ_DATA` 중 최소 하나(대부분 둘 다)는 있으나 4탭 심화 콘텐츠(`dayInLife`/`goodFit`/`missions`) 전무 |
| **완전 미충족(정적·퀴즈·심화 모두 없음)** | — | 합집합 정의상 존재하지 않음(정적 또는 퀴즈 중 최소 하나는 있어야 목록에 포함됨) |

즉 **"5개 축 완전 충족" 직업은 전체 127개 중 4개(3.1%)뿐**이며, 그중에서도 실제 사용자에게 노출 가능한 것은 1개(0.8%)뿐이다. 나머지 123개는 하는 일/필요한 힘/하루 모습/해보기에 해당하는 텍스트가 기존 정적 문서형 레이아웃(설명/좋아하면 잘 맞아요/작은 미션/부모 대화 질문 등, `OCCUPATIONS` 배열의 필드들)에 산재되어 있을 뿐, **4탭 구조로 재배치된 상태가 아니다**.

## 5. DB·정적 폴백·화면 렌더링 데이터 흐름

### 5.1 `/explore/[id]` 렌더링 우선순위(실측, `src/app/explore/[id]/page.tsx`)

```
1. supabase.from("occupation_master").select(...).eq("legacy_occupation_id", id).eq("is_active", true).maybeSingle()
   ├─ 행 있음 → mode: "db"
   │    ├─ occupation_summary(one_liner/easy_description/why_this_job)
   │    ├─ occupation_preparations(mission_hint/step_action)
   │    ├─ occupation_goyo24_profile(참고 지표, 없으면 "준비 중")
   │    └─ occupation_master(parent_occupation_id 기준 관련 직업, 037 hierarchy)
   └─ 행 없음(또는 오류) → mode: "static"
        └─ OCCUPATIONS.find(o => o.id === id) → 없으면 mode: "not-found"

2. (mode와 독립) isDreamMapActive 판정
   └─ true면 dreamMapDepth = OCCUPATION_DEPTH_SEED[id] (§3.1 표의 소스 혼합)

3. (mode/dreamMapDepth와 독립) quizData = QUIZ_DATA.find(q => q.occupationId === id)
   └─ 있으면 항상 퀴즈 섹션 렌더
```

### 5.2 우선순위 표

| 우선순위 | 데이터 원천 | 적용 조건 | 현재 QA 실측 커버리지 |
|---|---|---|---|
| 1 | `occupation_master` + 부속 테이블(DB) | `is_active=true` 행 존재 | 10개 직업만(§2.2) |
| 2(1의 fallback) | `OCCUPATIONS`(정적) | DB에 없거나 오류 시 | 67개 직업 |
| 독립 오버레이 | `OCCUPATION_DEPTH_SEED`(정적, 심화) | flag+화이트리스트+나침반 모드 | 4개 직업(노출 가능은 1개) |
| 독립 섹션 | `QUIZ_DATA`(정적) | DB/정적 모드와 무관 | 111개 직업 |

## 6. 데이터 일원화 판정

### 판정: **D — 직업별 혼합 구조로 전수 적용 전 별도 설계가 필요함**

**근거**:
1. **소스가 3개로 분산되어 있다**: `occupation_master`(DB, 10개 QA 활성) / `OCCUPATIONS`(정적, 67개) / `OCCUPATION_DEPTH_SEED`(정적 심화, 4개) + `QUIZ_DATA`(정적, 111개)까지 총 4개 파일·테이블이 각각 다른 직업 부분집합을 담당한다.
2. **동일 탭이 모드에 따라 다른 소스를 참조한다**(§3.1): "하는 일" 탭이 DB 모드에서는 `occupation_summary.one_liner`, 정적 모드에서는 `occupation.description`을 쓴다. 두 문구가 서로 다르게 작성되면 같은 직업이라도 DB 활성화 여부에 따라 사용자가 보는 문장이 달라질 수 있다.
3. **심화 시드(4개)와 DB 활성 목록(10개)이 완전히 분리되어 있다**(교집합 0개, §2.2). 전수 적용 시 "심화 콘텐츠를 어느 원천에 쓸 것인가"를 직업마다 다시 정해야 하며, 지금 상태로 그대로 확장하면 DB 활성 10개와 나머지 117개가 서로 다른 코드 경로를 타게 된다.
4. **QA의 DB 카탈로그 자체가 목표치(문서상 104개)에 크게 못 미친다**(§2.3). DB를 단일 원본(A안)으로 삼으려면 먼저 QA에 나머지 seed migration을 적용해야 하는데, 이는 이번 GOAL과 별도의 대규모 작업이며 이번 GOAL의 금지 범위(migration 실행)에도 해당한다.
5. **정적 데이터를 단일 원본(B안)으로 삼는 것도 완전한 해법은 아니다**: `OCCUPATIONS`(67)와 `QUIZ_DATA`(111)조차 서로 74개가 어긋나 있어(§2.2 표에서 한쪽에만 있는 직업들), 정적 데이터끼리도 이미 두 파일 간 정합이 깨져 있다.

**전수 적용 전 반드시 먼저 결정해야 할 것**(다음 GOAL에 위임, 이번 GOAL에서 결정하지 않음):
- 심화 4탭 콘텐츠를 **정적 파일(`OCCUPATION_DEPTH_SEED` 확장)로 전수 작성**할지, 아니면 **DB(`occupation_summary` 등)로 이전**할지 방향 결정
- `OCCUPATIONS`와 `QUIZ_DATA`의 직업 목록 불일치(74개 편차)를 먼저 정리할지, 아니면 이번 심화 작업과 별개로 남겨둘지 결정
- `DREAM_MAP_OCCUPATION_IDS` 화이트리스트를 전수 확장할지, 아니면 심화 콘텐츠 작성과 노출 게이트 해제를 분리된 별도 단계로 둘지 결정

## 7. 직업별 콘텐츠 작성 템플릿

기존 `docs/occupation-100-expansion-plan.md` §9(직업 1개 추가 표준 템플릿)는 **기본/얕은 계층**(occupation_master·summary·preparations·quizData·goyo24_profile)의 템플릿을 이미 상세히 문서화하고 있다. 이번 문서는 그 문서를 대체하지 않고, **심화 4탭 계층**(`OCCUPATION_DEPTH_SEED`)에 특화된 템플릿만 신규로 정의한다.

```typescript
// src/data/occupationDepthSeed.ts 에 추가할 항목의 표준 골격
"{legacy_occupation_id}": {
  occupationName: "{한국어 직업명, occupation_master.name_ko / OCCUPATIONS.name과 일치}",

  // 하루 모습 탭 — 4문장 내외, 아침→점심→오후→마무리 흐름 권장
  dayInLife:
    "{직업}은/는 {통념과 다른 실제 업무 특성 한 문장}.\n" +
    "먼저 {업무 흐름 1단계}.\n" +
    "그다음 {업무 흐름 2단계}.\n" +
    "마지막에는 {업무 흐름 3단계, 마무리/다음 준비}.",

  // 필요한 힘 탭 — "좋아하면 잘 맞아요" 톤, 재능 단정 금지
  goodFit:
    "{구체적 행동/취향}을 좋아한다면 {직업}이라는 직업을 재미있게 느낄 수 있습니다.\n" +
    "{또 다른 구체적 취향}을 좋아하는 아이에게도 잘 맞을 수 있습니다.\n" +
    "다만 {단일 재능}만 중요한 것은 아닙니다.\n" +
    "{꾸준함/협업/책임감 등 태도 요소}도 중요합니다.",

  // 해보기 탭 — 최소 1개, 권장 3개(오늘/이번 주/부모와 함께)
  missions: [
    { label: "오늘 해볼 것",     text: "{집에서 바로 실행 가능, 준비물 최소}" },
    { label: "이번 주 해볼 것",   text: "{며칠에 걸쳐 완성하는 활동}" },
    { label: "부모와 함께 해볼 것", text: "{대화 또는 관찰 중심, 위험 요소 없음}" },
  ],

  // 부모 대화 질문 — 정답 없는 개방형 질문 3~4개
  parentQuestions: [
    "{직업의 핵심 활동에 대한 흥미를 묻는 질문}",
    "{아이 스스로의 상상/선택을 묻는 질문}",
    "{직업의 두 가지 측면 중 선호를 묻는 질문}",
    "{직업을 갖게 된다면의 가정형 질문}",
  ],
},
```

**작성 순서 권장**: ① `dayInLife` 초안(해당 직업 실제 업무 조사) → ② `goodFit`(dayInLife에서 드러난 활동과 연결) → ③ `missions`(dayInLife에서 언급된 활동 중 아이가 직접 해볼 수 있는 것 추출) → ④ `parentQuestions`(missions 수행 후 나눌 대화).

| **`OCCUPATIONS`/`QUIZ_DATA` 목록 불일치로 인한 반쪽 심화** | 심화 시드를 추가해도 그 직업이 `QUIZ_DATA`에 없으면 퀴즈 섹션이 빠진 채로 노출되고(`chef`가 이미 이 상태), `OCCUPATIONS`에 없으면 정적 모드에서 "하는 일"/"필요한 힘"의 절반 소스(`occupation.description`/`occupation.skills`)가 아예 없어 렌더링 자체가 깨질 수 있음(현재 이 조합은 실제로 존재하지 않지만, 전수 확장 시 새 직업을 심화 시드에만 추가하면 발생 가능) | 다음 GOAL 착수 시 대상 직업이 최소 `OCCUPATIONS`에 존재하는지 선행 확인을 필수 게이트로 추가 |
| **초등 저학년(씨앗/새싹) 노출 범위 혼동** | 심화 4탭은 나침반 모드 전용이며 씨앗/새싹은 범위 밖(axis-standard §8-9) — 이번 GOAL의 "콘텐츠 표준"이 전 학년 대상처럼 오해될 수 있음 | 전수 콘텐츠 작성 시에도 노출 게이트는 나침반 모드로 유지, 씨앗/새싹 확장은 완전히 별도 GOAL로 취급(문서 §9 기존 방향과 일치) |
| **QA DB 카탈로그 목표치 미확정** | §2.3의 104개가 현재도 유효한 목표인지 미검증 | 다음 GOAL 착수 전, DB 경로를 택할 경우에 한해 PROD 실제 상태를 대표님께 확인받는 것을 선행 조건으로 제시(이번 GOAL은 PROD 접근 금지로 스스로 확인 불가) |
| **대량 카피 작성의 반복 문구화** | 123개 미충족 직업을 짧은 기간에 채울 경우 문장 패턴이 복제될 위험이 가장 크다 | §8 체크리스트의 교차 대조 항목을 다음 GOAL에서 카테고리별 배치 작업 단위로 강제 적용 권장 |

**차단 조건**(다음 GOAL에서 아래 중 하나라도 발생하면 즉시 중단해야 함): PROD host 감지, DB 경로 선택 시 사용자 승인 없는 SQL 실행, `OCCUPATION_DEPTH_SEED` 확장이 `OCCUPATIONS`/`QUIZ_DATA` 중 어느 쪽에도 없는 신규 직업 ID로 진행되는 경우(§10 두 번째 위험 참고).
